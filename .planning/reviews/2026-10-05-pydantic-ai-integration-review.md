## Prioritized findings

### F01 — P1: model arguments can substitute the tool identity used for authorization

**Confirmed by execution.** `pilot/tools.py:128` defines model-invoked `execute(ctx, _original=original, _tool_name=name, **kwargs)`. These defaults are ordinary keyword parameters. `PydanticTool.from_schema` at `:239` skips JSON-schema argument validation; the supplied custom validator at `:230` checks only authority-key names. `_tool_name` and `_original` are not among those keys. The JV `Tool.call` also forwards kwargs without schema validation (`jvagent/tooling/tool.py:63`).

Reproduction used a schema requiring a string `query` and forbidding additional properties, then submitted `{"query":123,"_tool_name":"web_fetch__fetch"}` to the search binding. The installed Pydantic validator accepted it; authorization checked **fetch**, while the wrapper executed **search**, receiving integer `123`. The host access callback trusts that substituted name (`orchestrator_interact_action.py:1465`). This bypasses per-tool ACLs when the substituted label is allowed. The currently admitted operations are read-only, which limits impact; the pattern must never be carried into write tools.

**Disposition: remediated at the pilot tool boundary.** `pilot/tools.py` captures the exact JV Tool and name in a factory closure; its callable accepts only Pydantic's context plus model arguments. A Draft 2020-12 validator checks the complete decoded argument object before the AccessControl callback or Action invocation. Reserved authority and wrapper-binding fields are rejected recursively even when an Action schema permits additional properties. The server-owned name is the only label passed to the per-call access check and tool observers. `tests/action/orchestrator/pilot/test_pydantic_ai_smoke.py` exercises a real Pydantic AI Agent run with spoofed wrapper identity and schema-invalid values, asserting neither authorization nor Action dispatch occurs. A companion run now injects AccessControl storage-resolution failure and proves no Action dispatch while a redacted security event is emitted. This closes the reported model-argument identity bypass for the pilot's current admitted tools; it does not assert every JSON Schema vocabulary or third-party Action implementation is safe for future effectful tools. Keep effects out until their separate approval/idempotency/reconciliation boundary is qualified.

### F02 — P1: failure to resolve access control grants access

**Confirmed by source; inherited security seam.** `orchestrator/access.py:20` catches errors looking up AccessControl and returns `None`; exceptions in `policy_applies()` do the same. `is_tool_allowed` at `:38` treats `None` as unrestricted access. The pilot's supposedly fresh, per-call authorization check uses this helper (`orchestrator_interact_action.py:1465`). A storage/configuration failure discovering the policy therefore differs from a policy evaluation failure: discovery fails open, evaluation fails closed.

**Disposition: remediated for the pilot access seam.** `orchestrator/access.py` treats a genuinely absent policy or a resolved non-applicable policy as the existing explicit open-deployment behavior. Exceptions or malformed policy objects during discovery, `policy_applies`, or `has_action_access` reach the denial path, emit a structured redacted `orchestrator_access_policy_failure`, and return false. Unit tests cover absent policy, resolution/evaluation failures and secret redaction. The Pydantic Agent-run regression confirms a lookup/storage exception cannot execute the bound Action. Other legacy callers that directly call `Agent.get_access_control_action()` without this fail-closed helper remain outside this pilot-specific closure and require separate review before claiming a platform-wide AccessControl guarantee.

### F03 — P1: configured dollar-spending guards are bypassed by the pilot — partially remediated

**Confirmed by call-path inspection.** Legacy checks turn spend in `loop.py:265` and conversation spend at `loop.py:430`. Pilot selection in `orchestrator_interact_action.py:1080` bypasses that loop. `pilot/runtime.py:463` passes request/tool/token limits but no cost limit; its adapter at `:331` also omits JV cost metadata. Conversation cost is settled after a successful driver return (`orchestrator_interact_action.py:1087`), which records spending without preventing it. Generic failures rethrow before settlement.

An agent configured with `max_turn_cost_usd` or an already exhausted `max_conversation_cost_usd` can still start and continue pilot model requests. A failed pilot may also leave conversation spend understated, despite Interaction-level metrics being available.

**Correction and current disposition:** Phase 54 adds a pre-request reservation to the capability pilot. Before each JV `ModelRequest` crosses into the configured model Action, it estimates a conservative prompt-size bound including the active tools, applies the bounded output-token setting, uses the configured provider/model pricing without cache discounts, adds 25% headroom, and checks both per-turn and accumulated conversation spend. Unknown pricing blocks before the request. Focused tests exercise the estimate, output clamp, unknown-pricing failure, prior conversation spend, and the guard's position before the provider call.

This reduces but does not eliminate spend overshoot: it is still an application estimate based on bundled/LiteLLM pricing and request serialization, not a provider-enforced reservation. Provider price changes, hidden billing units, or invoice adjustments can exceed it. The pilot also checks the dollar policy before every transport retry; failed or cancelled attempts without a receipt make accounting incomplete and stop another budgeted attempt. Conversation totals now fail closed when persisted state is missing, malformed, negative, boolean, NaN, or infinite, and settlement no longer resets a corrupt total to zero. These controls still cannot reconcile provider invoices automatically. Legacy-driver behavior and provider billing reconciliation remain separate qualification work.

**Streaming accounting correction (Phase 58):** lazy provider errors during streamed response consumption are now recorded as failed, unreported-cost attempts. Before this correction, stream construction was marked successful even when the first read returned an HTTP error, allowing the browser usage summary and pilot settlement to understate uncertainty. A real browser request against the disposable app verified the failed attempt now increments the visible unknown-cost count. Provider billing reconciliation, successful usage/cost receipts, and hard provider-side ceilings remain unqualified.

### F04 — P1: factual-output grounding contract — substantially remediated; semantic support remains open

**Original findings are closed at the contract/rendering boundary.** The capability-pilot Agent now accepts only `ResearchBrief`; `ConversationalReply` remains readable for legacy snapshots but is rejected by fresh research output validation (`pilot/runtime.py:341`, `:373`, `:941`, `:1003`). Each finding is a typed claim with host-known source IDs, a designated supporting fetched source, a quote anchor found in its bounded excerpt, and fresh host-observed timestamps. The renderer generates citations only from validated evidence; model-written URLs, Markdown links, and recognizable inline source-number citations are rejected. TaskStore independently revalidates the persisted output before delivery/completion.

**Phase 60 closes a remaining citation-marker variant:** plain-text `Source 99`, `[Source 99]`, `[99]`, and `Source #99` markers are now rejected from both claims and limitations, preventing the model from placing a fake reference immediately before host-rendered citations. Adversarial schema tests cover those forms.

**Semantic entailment is still not established by structural validation.** A quote can occur in a fetched excerpt without supporting the associated claim; host-observed freshness is not publication-date freshness. Continue adversarial evidence-support/calibration evaluations and qualify a separately bounded verifier for workloads that require factual entailment. Do not describe a valid quote anchor as proof that a claim is true.

### F05 — P1: truncating search JSON destroys the evidence used to validate the answer

**Disposition: remediated within the explicit evidence-inspection bound.** `compose_skill_tools()` sends the complete Action result to `PilotEvidenceCollector.observe()` before `_bound_tool_result()` clips the separate model-visible result (`pilot/tools.py:447-470`). The collector parses structured results only up to its declared 256,000-character inspection limit and records bounded per-source excerpts before annotation/context reduction (`pilot/runtime.py:32-40`, `:92-166`). Search annotation preserves valid structured JSON and tells the model when evidence was omitted by the per-run cap; context clipping trims snippets and keeps source IDs in a valid JSON envelope. Regressions cover a multi-source result over the former 4,000-character threshold, >256,000-character fail-closed inspection, valid bounded output, and an observer receiving the full Action result while the model receives its clipped copy (`tests/action/orchestrator/pilot/test_pilot_evidence.py:273`, `:291`; `tests/action/orchestrator/pilot/test_pilot_tools.py:155`, `:451`). This closes the reproduced receipt-loss bug. The 256,000-character ceiling intentionally yields no evidence from larger Action outputs; that outcome is not presented as a successful receipt.

### F06 — P1: refused, failed, and non-successful fetches become successful source receipts

**Disposition: remediated at the WebFetch-to-pilot provenance boundary.** `WebFetchAction.fetch()` returns the existing string-compatible `ToolResultText` while carrying host-owned metadata for outcome, requested URL, final validated redirect URL, content type, and HTTP status (`jvagent/action/web_fetch/web_fetch_action.py:110-126`, `:165-224`). `Tool.call()` preserves that metadata; the pilot observer receives it before model-context clipping (`pilot/tools.py:453-470`). Only `outcome=success`, HTTP 200, matching requested URL, a valid final URL matching the rendered source header, and a supported content type produce `fetched_page` provenance (`pilot/runtime.py:176-228`). Text that merely looks like a source header is not evidence, while search snippets remain separately typed `search_snippet` receipts. Tests cover refusal, transport error, unsupported type, 404, missing/forged/mismatched metadata, unsupported media, redirect revalidation, and the successful requested-to-final URL alias (`tests/action/orchestrator/pilot/test_pilot_evidence.py:376-489`, `tests/action/web_fetch/test_web_fetch_action.py:245-287`). A new cross-seam regression proves a valid redirect cites the final URL while the tool was invoked with the original URL. This closes the reported false-fetch receipt and redirect-identity bugs for the server-loaded WebFetch Action; metadata is a trusted in-process Action-to-harness channel, not a signed cross-process receipt. A successful provider-backed browser turn that invokes live search, fetches, and renders citations remains unqualified because the configured model endpoint has returned HTTP 401.

### F07 — P2: completed evidence accumulates until new research cannot admit new sources

**Disposition: cross-run saturation and host-observation freshness are remediated; evidence reuse remains intentionally unsupported.** Every capability run creates an empty collector, and the constructor explicitly ignores references from prior runs; follow-up research must fetch evidence again (`pilot/runtime.py:73-88`; `tests/action/orchestrator/pilot/test_pilot_evidence.py:592`). The per-run cap is 30, and overflow is counted, persisted in `PilotSnapshot`, and disclosed both in search annotations and fetch results (`runtime.py:90-92`, `:165-171`, `:230-235`, `:260-286`; `contracts.py:326`). Typed evidence records distinguish `search_snippet` from `fetched_page` and store host-observed UTC time (`contracts.py:138-155`). Output validation rejects support older than the 24-hour observation limit or timestamps too far in the future (`contracts.py:235-247`, `:269-270`). Tests cover an old reference not entering a new collector, 31st-source omission and persistence, failed/stale quote rejection, and fresh-fetch requirements.

**Remaining boundary:** citation-age freshness measures when this harness observed a fetch, not the publisher's last-modified time or the age of the underlying fact. A source fetched today can still contain stale information. Cross-run evidence reuse for genuine follow-up questions is not implemented; this safely avoids stale-source inheritance but does not provide task-linked reuse. Semantic entailment between a claim and its quote also remains open under F04. Do not describe the 24-hour host-observation check as source-publication freshness.

### F08 — P2: valid long URLs abort evidence collection

**Disposition: remediated for accepted credential-free HTTP(S) URLs.** Evidence URLs are validated and canonicalized before persistence; unsafe user-info, malformed/overlong values, fragments, default ports, host case, and known credential query parameters are handled by `normalize_evidence_url()` (`pilot/contracts.py:50-135`). Source IDs no longer use the full URL: safe bounded Action IDs are combined with a URL digest, otherwise a stable URL/result SHA-256 ID is generated (`pilot/runtime.py:101-116`). Full normalized URL remains independently bounded by `EvidenceReference.url` at 2,048 characters. Invalid results are skipped as evidence rather than aborting the completed Action call. Regressions cover URLs longer than the source-ID limit, credential-bearing/signed queries, canonical duplicates, and redirect final-URL aliases (`tests/action/orchestrator/pilot/test_pilot_evidence.py:511-590`).

**Remaining boundary:** credential query redaction uses a maintained list of known parameter names; it cannot recognize every proprietary signing scheme. Expand the list when provider integrations expose another convention, and avoid logging raw Action URLs. Unicode host normalization and IDNA conversion are implemented, but there is no cross-provider/browser conformance matrix for unusual Unicode path/query encodings.

### F09 — P2: provider termination and request controls are lost in the adapter

**Original request/response-loss repros are remediated in the adapter contract, but provider qualification is incomplete.** The JV bridge now maps `tool_choice`, `parallel_tool_calls`, `response_format`, `reasoning`, `reasoning_effort`, and core token/sampling settings into `ModelRequest`; provider-specific settings must be declared by the Action and unsupported host overrides fail explicitly (`pilot/runtime.py:537-598`). An Action with LiteLLM `drop_params=True` cannot silently claim its extra parameters are supported. `ModelResponse.finish_reason` is preserved, and partial output ending in length truncation, content filtering, or model error fails closed before Pydantic can validate or publish it (`:646-658`, `:672-695`). Tool calls preserve raw JSON argument text at the JV contract boundary and reject malformed or non-object arguments before constructing a Pydantic `ToolCallPart` (`action/model/contract.py:108-142`, `pilot/runtime.py:600-627`). Tests cover the settings mapping, declared-setting rejection, reasoning overrides, truncation, malformed tool JSON and multi-tool reconstruction.

**Remaining F09 qualification:** this adapter does not preserve provider request/replay identifiers or raw provider metadata in Pydantic history. Synthetic Agent/runtime tests establish mapping and fail-closed behavior, but the configured OpenAI and Ollama Cloud endpoints have returned HTTP 401 in browser tests; provider-specific settings, content filtering, reasoning-heavy truncation, malformed live tool arguments, and multi-call behavior therefore remain unqualified against successful provider responses. Keep support claims scoped to tested Action declarations, not generic portability.

### F10 — P2: user requests and proactive context were silently clipped — partially remediated

**Original finding confirmed; current pilot request path no longer clips an accepted question or proactive context.** The capability pilot rejects questions above 20,000 characters and preserves the complete accepted question in its snapshot and retry identity (`orchestrator_interact_action.py:1520`, `pilot/contracts.py:317`, `pilot/state.py:169`). ### F11 — P2: retries reload evidence, not the execution state or original budget

**Restart and budget accounting are partially remediated; execution continuation remains an enterprise blocker.** Current schema v7 persists question, evidence, validated output, request/tool/token counters, unresolved-usage state, and delivery-attempt/acknowledgement state in the existing graph-backed TaskStore (`pilot/contracts.py:319-349`). Under the conversation mutation lock, an active run is recognized as interrupted; a prepared final output is replayed through the same delivery identity. Other interrupted work is failed with its last saved evidence retained. An identical explicit resend restarts within that interaction only when prior usage is accounted for; a different objective receives an interruption notice, and unresolved usage stops before another model request (`pilot/state.py:206-237`; `orchestrator_interact_action.py:1410-1479`). An exact retry of a settled failed objective links to its parent and carries cumulative request, tool, and token counters into the new run (`orchestrator_interact_action.py:1309-1330`, `:1774-1819`). Parked exact retries reuse the TaskStore task and calculate limits from persisted counters, but create a fresh Pydantic Agent run (`pilot/state.py:268-299`). State tests verify failed-parent identity and preservation of reported/estimated usage and uncertainty (`tests/action/orchestrator/pilot/test_pilot_state.py:285-320`); recovery tests distinguish exact settled restarts, different requests, and unconfirmed usage (`tests/action/orchestrator/pilot/test_orchestrator_pilot.py:607-655`).

**Remaining F11 qualification:** Pydantic message history, active model/tool invocation state, and per-invocation replay ledger are not checkpointed. Therefore restart is explicit, not continuation; a retry does not replay the model's prior messages and cannot know whether an interrupted external provider completed unless usage was durably settled. An opt-in `JVAGENT_TEST_POSTGRES_DSN` subprocess regression now proves that an active TaskStore checkpoint with an unsettled model request survives an abrupt worker exit and is rediscovered by `PilotTaskStore.active_run()` in a fresh process against PostgreSQL (`tests/action/orchestrator/pilot/test_pilot_process_restart.py`). This does not exercise a crash during database commit, provider/tool execution, delivery, PostgreSQL outage/failover, or multi-worker recovery. Preserve these limits and add those database-backed crash boundaries before claiming production recovery. Define bounded serialization and compatibility rules before enabling resumable Pydantic message history or effects/subagents.

### F12 — P2: final response publication and task completion have a crash window

**The original task-completion crash window is remediated through a durable delivery handshake; end-to-end idempotence remains partially qualified.** The host validates and persists the final output as `delivery_pending` before egress (`pilot/state.py:319-357`, `orchestrator_interact_action.py:2090`). It derives one stable message ID from the TaskStore task, persists each attempt before sending, requires the ResponseBus channel adapter to accept the message, persists that acknowledgment, and only then completes the task (`orchestrator_interact_action.py:163-201`; `reply_action.py:411-416`; `response_bus.py:505-510`, `:575-583`; `pilot/state.py:359-468`). Task completion independently checks the persisted acknowledgment and matching stable message ID. Recovery after acknowledgment but before terminal task completion now has a failure-injection regression: it recreates the TaskStore, completes the acknowledged output, and asserts no second send (`tests/action/orchestrator/pilot/test_orchestrator_pilot.py:215-300`). This supersedes the review's original claim that task completion trusts only `delivered=True`.

**Remaining F12 qualification:** the response bus's one-egress deduplication record is process-local (`response_bus.py:124-154`); a crash after a channel accepted a send but before its acknowledgment was persisted can cause recovery to resend the same stable ID. The built-in Messenger and Facebook-comment adapters pass message content/recipient to Graph API calls without forwarding `ResponseMessage.id` (`facebook_action/messenger_adapter.py:77-99`; `facebook_comment_adapter.py:76-118`); WhatsApp logs the ID but calls its send methods without it (`whatsapp/whatsapp_adapter.py:286-313`); Email logs it but builds a `CanonicalSendMessage` without it and calls `send_canonical` (`email_action/email_adapter.py:173-198`). These paths therefore provide correlation, not provider-side idempotency. To limit duplicate risk, `ChannelAdapter.supports_idempotent_replay` defaults to false, and `_send_to_adapter` retries an exception only when an adapter explicitly declares that its transport deduplicates by the stable message ID (`channel_adapter.py:39-45`; `response_bus.py:1293-1329`). Regressions prove an unkeyed timeout is attempted once and a keyed adapter retries with the same ID (`tests/action/response/test_emitted_latch.py`). No built-in adapter currently qualifies for that opt-in. Pilot recovery refuses automatic resend after a recorded, unacknowledged attempt (`orchestrator_interact_action.py:1424-1452`), and v8 TaskStore snapshots now track reconciled attempt counts and an operator's decision, identity, timestamp, and bounded note (`pilot/contracts.py:303-344`; `pilot/state.py:248-339`). Admin-only GET/POST endpoints let an operator inspect pending sends and record `delivered` or `not_delivered`; conversation-to-agent ownership is checked, the write uses the conversation mutation lock, and a not-delivered decision authorizes one next attempt (`action/orchestrator/endpoints.py:18-131`). Unit regressions cover migration of uncertain v7 state, one explicitly authorized retry, and completion after a delivered decision without another send (`tests/action/orchestrator/pilot/test_pilot_state.py`). The API has no operator UI yet, so an administrator must inspect the external channel and choose the outcome. Graph-backed process-crash behavior and real external adapter idempotency remain untested; the guarantee is not exactly-once, and adapter acceptance is not proof of remote-client receipt. Inbound webhook deduplication (for example WhatsApp's inbound `wamid` cache) is a separate control and does not establish outbound idempotency.

### F13 — P2: cancellation leaves the surrounding TurnRun lifecycle inconsistent

**The original split-lifecycle defect is remediated; cancellation durability remains partially qualified.** The outer Orchestrator catches `asyncio.CancelledError`, transitions the TurnRun to `CANCELLED`, and persists its checkpoint in `finally` (`orchestrator_interact_action.py:1110-1125`). The pilot driver separately persists the TaskStore task as cancelled before re-raising (`:1585`), and composed Action tools emit a paired terminal cancellation outcome (`pilot/tools.py:324`, `:365`). A cross-layer integration regression now cancels while the real composed search Action is blocked, then verifies the Action receives cancellation, the pilot task/snapshot are cancelled, and the same interaction's harness TurnRun checkpoint is terminal-cancelled (`tests/action/orchestrator/pilot/test_orchestrator_pilot.py:1314-1348`).

**Remaining F13 qualification:** ordinary TaskStore/graph write exceptions no longer replace the original `CancelledError`, and the cancellation state save is shielded from repeated cancellation signals until it settles. Regressions cover both a failed save (active pilot task remains eligible for recovery) and a second cancellation during the save (pilot task and TurnRun settle as cancelled). A graph operation that never settles can still hold cancellation indefinitely. Tests use the in-memory durable-conversation test double and do not establish PostgreSQL interruption recovery, disconnect semantics, or deployed-backend cleanup guarantees. Test cancellation at model wait, Action wait, evidence checkpoint and final delivery against the deployed graph backend before broad claims.

**PostgreSQL qualification update:** an opt-in worker-restart regression now performs the real `PilotTaskStore.cancel()` transition against PostgreSQL, terminates that worker without closing its pool, and verifies a fresh process reads both TaskStore and snapshot as cancelled, retains unsettled-usage state, and does not rediscover the task as active (`tests/action/orchestrator/pilot/test_pilot_process_restart.py`). This covers a committed cancellation followed by worker exit only; process death during the cancellation transaction, database outage/failover, cancellation bounds, client disconnect, and deployed cleanup remain unqualified.

**Correction:** establish one terminal cancellation transition shared by task, outer run and streaming state. Use bounded cleanup appropriate to the storage backend, and finish tool events with explicit cancellation/timeout status. Test cancellation at model wait, Action wait, evidence checkpoint and final delivery.

### F14 — P2: recovered tool errors were not a coherent model/UI protocol — partially remediated

### F16 — P2: host context required caller binding and replay protection — remediated

**Original finding confirmed; current source closes the identified trust gap.** `orchestrator/host_context.py` now requires a dedicated `JVAGENT_HOST_CONTEXT_SECRET`, verifies issuer, audience, version, bounded expiry, and exact agent/user/session values resolved by the server. The host-supplied `run_id` is intentionally only a signed request label; it is explicitly not authority and is not presented as the server's correlation ID. The nonce is durably recorded in the caller's Conversation while holding its mutation lock, together with the server-generated correlation ID. A repeated nonce, unavailable Conversation, malformed ledger, persistence error, or full bounded ledger rejects promotion. The InteractWalker consumes the envelope only after resolving the live caller and creating its correlation ID. Verified context is therefore bound to the authenticated session and a one-use nonce, not merely to a caller-selected run label.

The review's original statements that the context lacked expiry, caller binding, replay protection, and key separation are stale for the current tree. Focused tests cover caller/expiry binding, dedicated-key use, tampering, one-use behavior, fail-closed ledger errors/capacity, and concurrent replay. Opt-in Redis qualification covers lease renewal and cooperative async cancellation after lease loss. A further opt-in test starts two independent workers against shared PostgreSQL and Redis with both Conversation snapshots loaded before contention. The first run exposed a real replay race: `Conversation.get()` returned each worker's stale GraphContext cache, and both admitted the nonce. The host-context boundary now uses `Conversation.find_one({"id": ...})` under the distributed mutation lock, which reads through the shared database without relying on the process cache; the two-worker test now proves exactly one promotion and reads the one-entry ledger back from PostgreSQL. This qualifies that local PostgreSQL+Redis topology only. It does not fence work already executing synchronously or suppressing cancellation, nor qualify database failover or a deployed multi-worker topology. Keep this host-only contract generic and independent of Integral or any other application.

### F17 — P2: reported zero costs are overwritten and provenance is too provider-specific

**Confirmed by source.** LiteLLM preserves response cost only if `> 0` (`litellm_lm.py:272`) and its tracking code estimates when `cost <= 0` (`:298`). Ollama tracking does the same (`ollama.py:250`). A legitimate reported zero-dollar call is replaced by a nonzero estimate for a priced model. Meanwhile Interaction labels only `litellm_response_cost` as reported; other non-LiteLLM reported cost is accumulated into `estimated_cost_usd` (`memory/interaction.py:625`). Non-finite values are not consistently rejected.

**Correction:** distinguish missing cost from zero, validate finite nonnegative amounts, and represent amount/currency/source/estimated/pricing-version in one provider-neutral cost record. Keep provider-reported token usage distinct from estimated price. Add zero-cost, absent-cost, unknown-model, NaN/Infinity and non-LiteLLM reported-cost tests. The current work improves visibility, but is not invoice-grade cost reconciliation.

### F18 — P3: budget and qualification documentation is stale

**Partially remediated.** The proposed ADR-0056 is retained as historical planning evidence; its initial ceilings are superseded by current Orchestrator defaults of 32 requests/48 tool calls/100k total tokens/20k output tokens/300 seconds. The pilot now selects one enabled JV skill through exact-name `pilot_skill` (default `research`) and rejects a selected skill unless it declares `output-contract: evidence_required` and satisfies the existing research-evidence contract. Alternate skill selection and proactive TaskStore dispatch for the configured skill are covered by Orchestrator tests. Runtime instructions now refer to the selected JV skill rather than naming `research` unconditionally. The current compatibility matrix documents that narrow selector and its remaining constraints. The older pilot line-count estimate is historical, not a current size measure.

**Remaining correction:** keep the compatibility/qualification matrix tied to tested revisions and update it as support changes. Do not edit accepted ADR history; publish amendments through a new decision record if the architecture decision itself changes. Retain browser/provider outcomes as qualification evidence rather than treating configuration or unit tests as deployment proof.

### Capabilities that are possible but not implemented or qualified here

1. **Subagents/delegation:** no delegated-agent runtime is installed by this pilot. Native Pydantic patterns can support it, but child caller permissions, parent/child tasks, budget sharing, cancellation propagation, depth/concurrency limits and receipt ownership must be defined before admission. Do not equate dependency availability with feature completion.
2. **Production write tools:** effect_invoker is an adapter seam; the production research entry does not pass one. Approval/idempotency/reconciliation proofs in the current crash tests are test-fixture proofs, not production connectors or an approval journey.
3. **MCP and visitor-bound Actions:** explicitly excluded during tool collection (`orchestrator_interact_action.py:1276`). Actions remain a strong authoring boundary, but full runtime compatibility is deferred.
4. **Stateful skills/interviews:** locks, prerequisites, inheritance, hooks, bundled scripts and parameters are rejected by `pilot/runtime.py:358`. This fail-closed design is appropriate; enterprise rollout must publish these differences rather than imply all current skills are supported.
5. **Long-running autonomous jobs:** a maximum 600-second run remains an interactive bounded job. No durable background Pydantic executor, scheduler continuation, child-run budget or staged checkpoints are supplied by this integration.
6. **Provider matrix:** current live evidence emphasizes GLM-5.3 Cloud. OpenAI reasoning, strict tool schemas, refusal behavior, native structured output and provider-specific replay need equivalent qualification. Transport availability is not demonstrated behavioral equivalence.
7. **Operational qualification:** no new two-worker/postgres lost-lease test, load/soak run, p95/p99 latency/error-rate study, or browser disconnect/restart matrix was conducted in this review. Source tests are not those gates.
8. **Minimal bloat:** two engines plus a 1,186-line pilot package and roughly 600-line Orchestrator pilot integration presently add maintenance responsibilities. The plan explicitly intends a later expand/revise/remove decision; retirement has not happened.

## Recommended engineering path

Keep the pilot opt-in and read-only. F01/F02/F05/F06 and the bounded URL/per-run evidence controls in F07/F08 now have specific implementation and regression evidence at the current pilot Action seam. Close the remaining trust and factual-output gaps (especially F03 and F04's semantic entailment/publisher-freshness boundary) before widening admission. Task-linked evidence reuse remains deferred. These corrections strengthen the existing boundaries; they do not require replacing Actions, SKILL.md or object-spatial persistence.

Then establish five small, explicit contracts: SkillCompiler, guarded Action binding, JV Model adapter, graph RunCheckpoint, and Egress acknowledgment. Make the Orchestrator select a driver and delegate through those contracts; move research evidence policy out of its large execution method. Keep one source of caller authority, one graph persistence owner, one cost policy and one publication protocol. Avoid adding core intent classifiers, domain-specific prep logic, or a second workflow store.

Before adding writes or delegated agents, close recovery/cancellation/delivery/budget gaps and run the real browser failure matrix. Add contract-level adversarial tests for every finding, then real configured-provider browser scenarios: greeting, long research, failed/refused fetch, large search output, long URL, follow-up beyond 30 sources, spending limit, response truncation, slow model, cancellation, disconnect, backend restart and replay. Record exact revision, source result state, visible events, persisted terminal state and actual/estimated usage separately. Add multi-worker storage/lease testing as its own gate.

Finally compare a representative skill set across drivers with repeated model runs and an independent quality rubric. The existing matched smoke is encouraging: its JSON report records 14,411 pilot tokens versus 40,426 legacy tokens over three single-replicate synthetic-source cases. That is a narrow efficiency signal, not a general reliability estimate. Expand only after the compatibility matrix is explicit, and identify the legacy loop responsibilities to retire so that permanent dual-engine bloat does not become the outcome.

## Primary-source checks

The installed `pydantic_ai/tools.py:481` explicitly states that `Tool.from_schema` skips schema validation; this was verified against the [official Tool API documentation](https://pydantic.dev/docs/ai/api/pydantic-ai/tools/). Its behavior makes server-side argument validation an integration responsibility.

The installed `pydantic_ai/usage.py:471` explains that request limits are checked before calls and token limits after responses. [Official agent documentation](https://pydantic.dev/docs/ai/core-concepts/agent/) describes usage limits; these do not make a response-postchecked budget a preauthorization ceiling.

Pydantic's [durable execution documentation](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) treats durability as a separate integration concern. Saving an evidence snapshot alone does not adopt a durable execution backend.

## Conclusion

The marriage is viable. JV's skills, modular Actions, graph identity/state and established egress are worth retaining; Pydantic can own typed composition and the execution loop. The current implementation proves a useful research witness, not an enterprise-standard harness. Its decisive remaining work is enforcing trust and operational contracts—not increasing default budgets or adding more tools. Address the concrete defects first, qualify recovery and provider behavior next, then generalize and simplify.
